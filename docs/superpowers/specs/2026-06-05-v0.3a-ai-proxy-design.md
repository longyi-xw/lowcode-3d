# v0.3 sub-stage A — AI proxy + BYO-key + provider 配置 设计

**状态**: 已批准（2026-06-05）
**前置**: v0.2 完成（资源库 #29 + 材质编辑 #30）。
**定位**: v0.3「AI Skill 框架」的第一个 sub-stage（基础设施）。第二个 sub-stage B（Skill 框架 + scene-edit 加灯 + 自然语言输入 UI）依赖本期。
**架构依据**: `design/framework/architecture.md` §4.3（Skill 接口）、§一（BYO-key：OpenAI/Anthropic/本地 Ollama）、§二（`src-tauri ai/` = AI 调用代理防 key 泄漏）。

---

## 1. 目标

提供调用 LLM 的 Rust 端 proxy（本期 Anthropic）+ 安全的 BYO-key 存储（OS keychain）+ Settings 配置 UI，让后续 sub-stage B 的 Skill 能调通 LLM。API key 绝不进 renderer / bundle / 导出代码 / 日志。

## 2. Success criteria

1. Settings「AI providers」能填 Anthropic API key（经命令存入 OS keychain，输入框不回显已存的 key）+ 选 model。2.「测试连接」按钮用真实 key 调通 Anthropic，成功/失败有明确反馈（toast）。
2. `ai_complete` 命令可被调用，返回纯文本补全；传 `json_schema` 时返回结构化 JSON（为 B 铺路）。
3. key 不出现在 renderer 内存之外能观测的任何地方（bundle / 导出 / 控制台日志 / Scene JSON）；`has_ai_key` 只返回布尔。
4. `cargo test`（Rust 纯函数单测）+ `pnpm lint && pnpm typecheck && pnpm test`（前端）全绿 + `pnpm tauri dev` 人工验证（需用户 Anthropic key）。

## 3. 范围

### In scope

- Rust `src-tauri/src/ai.rs`：`AiProvider` 抽象（本期仅 `Anthropic`）+ Anthropic Messages 客户端（reqwest）+ keychain（keyring crate）。
- Tauri 命令：`set_ai_key` / `has_ai_key` / `clear_ai_key` / `ai_complete` / `test_ai_provider`（specta → `src/bindings/tauri.ts`）。
- 前端 `src/services/ai/proxy.ts`：封装命令 + 读 settings provider/model。
- settings store 加非密配置 `aiProvider` / `aiModel`。
- Settings UI「AI providers」section。
- settings i18n（`ai.*`）。

### Out of scope（B 或 Backlog）

- **Skill 接口 / 注册表 / 执行循环**（sub-stage B）。
- **自然语言输入 UI**（sub-stage B）。
- **OpenAI / Ollama provider**（留 enum 抽象，后续加分支）。
- skill→Command 映射、scene-edit 加灯（B）。

## 4. 数据模型 / 类型

Rust 侧（serde + specta，生成 TS bindings）：

```rust
// 本期仅 Anthropic;加 provider = 加 enum 分支。
// #[serde(rename_all = "lowercase")] → 序列化为 "anthropic",与前端 settings.aiProvider
// + keychain account 字符串一致(消除大小写不一致)。
pub enum AiProvider { Anthropic }

pub struct AiCompleteRequest {
    pub provider: AiProvider,
    pub model: String,
    pub system: String,
    pub user: String,
    pub json_schema: Option<serde_json::Value>, // 有则强制结构化输出
}

pub struct AiCompleteResponse {
    pub text: Option<String>,  // 无 schema 时
    pub json: Option<serde_json::Value>, // 有 schema 时
}

pub enum AiError {
    NoKey,                                  // keychain 无该 provider 的 key
    Network(String),                        // 连接失败
    ApiError { status: u16, message: String }, // provider 返回非 2xx
    Parse(String),                          // 响应解析失败
}
```

前端 settings（localStorage，**非密**）：

```ts
// SettingsState 追加
aiProvider: "anthropic"; // 本期固定（union 预留）
aiModel: string; // 用户可填,默认一个 Anthropic model id
setAiProvider / setAiModel;
```

> key **绝不**进 settings / localStorage / 任何前端持久化。

## 5. 架构 / 组件（职责 + 数据流）

### 5.1 Rust `src-tauri/src/ai.rs`

纯函数（可单测）+ 命令胶水（手动验证）分离：

- `build_anthropic_body(model, system, user, schema: Option<Value>) -> Value`（**纯**）：组 Anthropic Messages 请求体。无 schema → 普通 messages；有 schema → 加 `tools: [{ name: "emit_result", input_schema: schema }]` + `tool_choice: { type: "tool", name: "emit_result" }`（强制结构化）。
- `parse_anthropic_response(body: Value) -> Result<AiCompleteResponse, AiError>`（**纯**）：`content[]` 里有 `tool_use` block → `json = input`；否则拼接 `text` block → `text`。
- 命令（async，胶水）：
  - `set_ai_key(provider, key)` → `keyring::Entry::new("lowcode3d-ai", provider_account)?.set_password(&key)`。
  - `has_ai_key(provider) -> bool` → keychain `get_password` 成功与否（不回传内容）。
  - `clear_ai_key(provider)` → `delete_credential`。
  - `ai_complete(req) -> Result<AiCompleteResponse, AiError>` → 取 key（无则 `NoKey`）→ `build_anthropic_body` → reqwest `POST https://api.anthropic.com/v1/messages`（header `x-api-key` + `anthropic-version: 2023-06-01`）→ 非 2xx → `ApiError` → `parse_anthropic_response`。
  - `test_ai_provider(provider, model) -> Result<(), AiError>` → 复用 `ai_complete` 发最小 ping（system="", user="ping", max 简短），成功即 Ok。

### 5.2 前端 `src/services/ai/proxy.ts`

封装 `commands.aiComplete/setAiKey/hasAiKey/clearAiKey/testAiProvider`（来自 `@/bindings/tauri`）；`aiComplete` 时从 `useSettingsStore` 读 `aiProvider`/`aiModel` 填入。错误（`AiError`）经现有 `reportError`/toast 反馈。

### 5.3 settings store + Settings UI

- `useSettingsStore` 加 `aiProvider`/`aiModel` + setters（persist v2，迁移加默认）。
- Settings「AI providers」section：provider 选择（本期只 Anthropic，禁用其余或仅显示一项）+ model 文本输入 + key 输入框（提交 → `setAiKey`；占位显示"已配置"当 `hasAiKey` 为真，不回显原 key）+「测试连接」按钮（→ `testAiProvider` → toast）+ 清除 key 按钮。

### 5.4 命令注册 + bindings

`src-tauri/src/lib.rs` 的 `collect_commands![]` 加 5 个新命令；`AiError`/`AiProvider`/`AiCompleteRequest`/`AiCompleteResponse` 经 specta 导出；`pnpm bindings` 重新生成 `src/bindings/tauri.ts`（git-tracked）。`Cargo.toml` 加 `reqwest`（json + rustls-tls，避免 openssl）、`keyring`、`serde_json`（若未有）。

## 6. 密钥安全

- key 只经 `set_ai_key` 命令从 renderer **单向**传入 Rust → keychain；之后 renderer 无任何取回路径（`has_ai_key` 仅布尔）。
- `ai_complete` 在 Rust 进程内取 key 拼 header，key 不回 renderer、不写日志、不入任何文件/Scene/导出产物。
- keychain service 名 `lowcode3d-ai`，account = provider（如 `anthropic`）。

## 7. 错误处理

`AiError`（specta enum）映射前端文案：`no_key`→"未配置 API key"、`network`→"连接失败"、`api_error`→显示 status+message、`parse`→"响应解析失败"。走现有 `reportError` → 持久 `toast.error`（沿用 3.3 错误处理约定）。

## 8. 测试策略（TDD）

- **Rust `cargo test`（ai.rs 纯函数）**：
  - `build_anthropic_body`：无 schema → messages 形状；有 schema → 含 `tools` + 强制 `tool_choice`。
  - `parse_anthropic_response`：text-only response → `text`；含 `tool_use` → `json`；空/异常 content → `Parse` 错误。
  - （keychain / 真实 HTTP 不单测——胶水层手动验证。）
- **前端 vitest**：`proxy.ts`（mock `@/bindings/tauri` 的 commands，断言读 settings + 调命令 + 错误映射）；Settings AI section（填 key → 调 `setAiKey`；点测试连接 → 调 `testAiProvider`；`hasAiKey` 真时显示已配置不回显）。
- **人工 `pnpm tauri dev`**（需用户 Anthropic key）：填 key → keychain 存 → 测试连接成功 → 重启应用 `has_ai_key` 仍真 → 清除后变假。验证 key 不出现在 devtools/网络面板的 renderer 侧、不在导出产物。

## 10. 风险

- **keyring 在 Linux 构建**需 secret-service/dbus（`release.yml` Ubuntu job 可能要 `apt-get install libdbus-1-dev`）——届时 CI/release 验证（类似 v0.1 macOS universal bundle 坑）。
- **真实 LLM 调用进不了 CI**（无 key）：核心逻辑（build/parse 纯函数）Rust 单测覆盖；连通性靠人工。
- **CI 是否跑 `cargo test`**：现有 CI 为前端 `Lint·Typecheck·Test`；Rust 单测作为本地/plan 内验证步骤，必要时在 CI 加 cargo test job（plan 阶段确认）。

## 11. 验收

满足 §2 success criteria：Settings 配 key（keychain 不回显）+ 测试连接调通 + `ai_complete`（text + 结构化）可用 + key 不泄漏 + Rust/前端测试绿 + 人工验证。完成后进入 sub-stage B（Skill 框架 + scene-edit 加灯 + 自然语言 UI）。
