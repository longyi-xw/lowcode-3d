## 6. 发布执行流程

1. **3.5 PR**：CHANGELOG + 三处 bump（+ Cargo.lock 同步）。lint/typecheck/test 绿 → push → `gh pr create` → CI 绿 → 回填 roadmap 3.5 → merge。
2. **tag（确认后）**：merge 后，在 main 最新 commit 上 `git tag v0.1.0 && git push origin v0.1.0`。**这一步 agent 在跟用户明确确认后才执行**（不可逆对外 + 触发 ~10–20min 三平台编译）。
3. **release.yml**：tag push 触发 → mac/Ubuntu/Win 构建 → 起草 draft Release（artifacts 附上）。agent `gh run watch` 观察构建结果。
4. **publish（用户）**：draft 成功后，**用户**在 GitHub review draft + 把 CHANGELOG `[0.1.0]` 段落贴入 release notes + 正式 publish。agent 不自动 publish。

## 7. Release notes

- 不改 `release.yml`（保持 `releaseDraft: true` 自动草稿）。
- CHANGELOG `[0.1.0]`（英文）是 notes 的权威来源；用户 publish 前贴入/编辑 draft。
- 未签名构建：draft/release 描述里提醒用户首次启动的系统警告（可选，用户 publish 时加）。

## 8. 验证策略

- 代码层无新逻辑 → 无单测。`pnpm lint && pnpm typecheck && pnpm test` 绿（确认版本 bump 不破坏；现 328 测试）。
- 一致性人工核对：三处 version 都是 `0.1.0`、tag 名 `v0.1.0` 与之匹配、CHANGELOG 日期/链接正确。
- 发布层验证（tag 后）：`gh run watch` 看 release.yml 三平台 job 全绿、draft Release 出现且带 artifacts。这是 3.5 真正的「测试」，耗时（多平台编译）。
- **回滚**：若构建失败或 draft 有误 —— 删 tag（`git push --delete origin v0.1.0`）+ 丢弃 draft，修复后重打。tag 未 publish 前都可回退。
